# 对话提示词与 RAG 上下文拼接逻辑梳理

更新时间：2026-04-28

本文梳理 ThinkFlow 普通聊天场景下，用户 query、对话绑定文档、输入框参考文档、左侧素材 RAG 检索片段之间应该如何拼接。

## 核心口径

当前版本不再使用“活跃文档”作为普通聊天 prompt 概念。

每个对话和一份文档是一一绑定关系。这个绑定文档是当前对话的产出/写入对象，主要用于推送、并入、保存和恢复对话工作状态。普通聊天时，绑定文档不因为绑定关系自动作为回答依据进入模型上下文。

普通聊天的回答依据只有两类：

```text
1. 输入框下方勾选的参考文档
   - 如果勾选全文，拼全文。
   - 如果勾选模块，拼选中模块。
   - 如果绑定文档也被勾选，它只是“参考文档”，不再额外出现一份“活跃文档”。

2. 左侧素材勾选后通过 RAG 检索得到的 chunk
   - 对话来源里出现素材标题不等于模型拿到了素材内容。
   - 素材正文必须通过 files -> vector store -> retrieved_chunks -> File Analyses 进入最终 prompt。
```

因此，普通聊天最终 prompt 的原则是：

```text
回答上下文 = 本轮工作区上下文 + 素材 RAG chunk + 独立对话历史 + 用户本轮问题。

对话绑定文档 = 写入/推送目标，不是默认回答依据。
```

## 为什么旧 prompt 会误导

之前模型自述自己看到了：

- 系统提示词
- 活跃文档
- 活跃文档当前焦点
- 参考文档 1
- 对话来源
- 用户新消息

这里有两个问题。

第一，“活跃文档”是旧交互逻辑残留。现在对话已经和文档一一绑定，不需要再把绑定文档包装成一个模型可见的“活跃文档”块。否则用户明明没有把该文档勾成参考文档，模型也会读到它的全文。

第二，“对话来源”只是来源目录，不是素材证据。比如：

```text
[对话来源]
- 来源 1: [material] Expert_attention____ACL_v2 (2).pdf
```

这只能说明当前对话关联了这个 PDF，不能说明 PDF 内容已经进入 prompt。真正可用于回答的素材内容应该出现在最终 QA prompt 的 `File Analyses` 中：

```text
File Analyses:
[1] --- [Expert_attention____ACL_v2 (2).pdf] ---
{RAG 检索到的相关 chunk}

Sources:
[1] Expert_attention____ACL_v2 (2).pdf
```

如果没有 `File Analyses`，模型无法真正基于 PDF 内容回答。

## 当前目标链路

普通聊天入口在前端 `handleNotebookChatMessage(query)`。

目标流程：

```text
1. 用户输入原始 query。
2. 前端调用 /kb/conversations/{conversation_id}/chat-context。
3. 后端返回：
   - context_text：用于最终回答的工作区上下文。
   - rag_query：用于 embedding/RAG 检索的短查询。
4. 前端调用 /kb/chat/stream：
   - files：左侧勾选素材对应的本地文件路径。
   - query：context_text。
   - rag_query：用户原始问题或短检索问题。
   - history：对话历史。
5. 后端 RAG 使用 rag_query 检索素材 chunk。
6. 最终 QA prompt 使用 context_text + File Analyses + history 生成回答。
```

## chat-context 阶段

`ThinkFlowChatContextService.build_context()` 负责生成工作区结构化上下文。

当前应该包含：

```text
[系统提示词]
你是 ThinkFlow 工作区里的 AI。文档只能通过用户显式推送动作被修改；普通聊天只回答问题。

[参考文档 N]
来自 source_refs 中 type=document/output_document 的文档。
如果该文档有选中模块，拼选中模块。
如果没有选中模块，拼全文截断。

[对话来源]
来源目录，包括 document/material 标题。
注意：material 这里只是目录，不是素材正文。

[用户新消息]
用户本轮输入。
```

当前不应该包含：

```text
[活跃文档]
[活跃文档当前焦点]
[文档变更摘要]
[对话历史消息]
```

活跃文档相关块属于旧的一对多/可切换活跃文档模型。新版本里，绑定文档只作为 workspace state metadata 返回，不进入模型可见上下文。

`[对话历史消息]` 也不放在 `context_text` 里。历史应该只通过 `/chat/stream.history` 独立传入最终 QA prompt，内容是每轮用户原始 query 和助手回答，不能把每轮组装后的 `context_text` 滚进下一轮。

## RAG / QA 阶段

`/kb/chat/stream` 接收：

```json
{
  "files": ["...selected material paths..."],
  "query": "...chat-context 生成的 context_text...",
  "rag_query": "...用户原始问题或短检索问题...",
  "history": []
}
```

后端 `_build_chat_request()` 构造 `IntelligentQARequest`：

```text
request.query = context_text
request.rag_query = rag_query or query
request.file_ids = files
request.vector_store_base_dir = notebook 对应 vector store
```

随后 `build_intelligent_qa_prompt(state)`：

```text
1. try_rag_retrieve(state)
   - 使用 state.request.rag_query 做 embedding 检索。
   - 使用 state.request.file_ids 限定左侧勾选素材。
   - 写入 state.retrieved_chunks。

2. build_doc_context(state)
   - 把 retrieved_chunks 格式化为编号来源片段。
   - 生成 source_mapping / source_preview_mapping / source_reference_mapping。

3. 生成最终 QA prompt：
   User Question: {context_text}
   File Analyses: {retrieved chunk context}
   Conversation History: {history}
```

最终模型看到的结构应该是：

```text
system:
You are a helpful AI assistant...

user:
You are provided with analyses from multiple files regarding a user's question.

User Question:
{系统提示词 + 参考文档 + 对话来源目录 + 用户新消息}

File Analyses:
{RAG 检索片段 + Sources mapping}

Conversation History:
{聊天历史}

Citation rules:
...
```

## 三个边界

### 1. 绑定文档不是默认参考文档

如果当前对话绑定了「梳理摘要 1」，但输入框没有勾选它：

```text
context_text 里不应该出现「梳理摘要 1」全文。
```

如果输入框勾选了「梳理摘要 1」：

```text
context_text 里出现 [参考文档 1]。
它可以是全文，也可以是选中模块。
它不再额外出现 [活跃文档]。
```

### 2. 对话来源不是素材正文

`[对话来源]` 里的 material 标题只用于说明来源关系和帮助调试。

真正的 PDF/素材正文必须满足：

```text
conversationSourceRefs(type=material)
-> selectedFilePaths
-> /chat/stream.files
-> vector store search
-> retrieved_chunks
-> File Analyses
```

任何一步断了，模型都只能看到素材标题，看不到素材内容。

### 3. answer query 和 rag query 要分开

`query` 用于最终回答，需要包含完整工作区上下文。

`rag_query` 用于 embedding 检索，应该短、聚焦，默认就是用户原始输入。

这样可以避免把参考文档全文、历史消息、来源目录一起塞进 embedding query，稀释检索意图。

## test427 的 RAG 排查结论

对 `test427 / Expert_attention____ACL_v2 (2).pdf` 做过本地链路验证：

```text
vector_store 存在：
outputs/765973346_at_qq.com/test427_local_1777265996281_288d15bd/vector_store

knowledge_manifest.json 中该 PDF 状态：
status = embedded
chunks_count = 30

短 query：
SHRP 的主要贡献和效果是什么？

RAG 检索结果：
retrieved_chunks = 30
```

因此这个 case 不是 embedding/vector store 整体挂了。

更可能的问题是：

```text
1. 旧 prompt 里绑定文档被显示成“活跃文档”，造成模型自述和用户理解混乱。
2. RAG chunk 在最终 QA prompt 的 File Analyses 里，不在 chat-context 里。
3. 如果只问模型“你看到了哪些提示词部分”，模型可能只描述 User Question 里的结构化上下文，不一定复述 File Analyses。
4. 如果前端没有把左侧素材传入 files，RAG 会跳过。
5. 如果 RAG 使用完整 context_text 做 query，检索可能被长上下文稀释，所以需要 rag_query。
```

## 已对齐的实现要求

- `chat-context` 返回 `context_text` 和 `rag_query`。
- `context_text` 不再包含 `[活跃文档]`、`[活跃文档当前焦点]`、绑定文档全文。
- `context_text` 不再包含 `[对话历史消息]`；历史只走 `/chat/stream.history`。
- 勾选参考文档时，参考文档全文或选中模块进入 `context_text`。
- 绑定文档也被勾选时，只作为 `[参考文档 N]` 出现一次。
- `/chat/stream` 接收 `rag_query`。
- RAG 检索使用 `rag_query`，最终回答仍使用 `query/context_text`。
- 左侧素材必须继续从 `conversationSourceRefs(type=material)` 映射到 `/chat/stream.files`。
- 助手回答里的引用 hover 数据只作为消息展示 metadata 持久化：
  - `content` 只保存助手原始回答文本，例如 `结论...[1]`。
  - `sourceMapping / sourcePreviewMapping / sourceReferenceMapping / fileAnalyses` 不拼进 `content`。
  - 下一轮 `/chat/stream.history` 仍只发送 `{ role, content }`，不发送展示 metadata。
  - 历史消息重新加载时，前端可以用 metadata 恢复引用右上标 hover，但这些数据不进入模型可见上下文。

## 验收标准

- 不勾选参考文档时，普通聊天 prompt 不出现绑定文档全文。
- 勾选参考文档时，模型能基于该文档全文或选中模块回答。
- 勾选左侧素材后，`/chat/stream.files` 包含该素材路径。
- 后端日志能看到 RAG 使用短 `rag_query` 检索。
- 模型回答能引用素材 chunk 编号，例如 `[1]`。
- 只列出 `[对话来源]` 但没有 RAG chunk 时，模型不应声称已经基于该素材正文回答。
- 对话历史只包含用户原始 query 和助手回答，不包含任意一轮组装后的 `context_text`。

## 一句话结论

现在普通聊天不再是：

```text
系统提示词 + 活跃文档 + 参考文档 + 对话来源 + 历史 + 用户新消息
```

而应该是：

```text
参考文档上下文
+ 用户 query 驱动的素材 RAG 检索片段
+ 独立传入的原始问答历史
+ 明确的回答与引用规则
```

其中：

```text
输入框参考文档 / 模块选择负责文档上下文。
左侧素材 checkbox / embedding 检索负责来源证据。
对话绑定文档只负责写入对象，不默认负责回答依据。
```
