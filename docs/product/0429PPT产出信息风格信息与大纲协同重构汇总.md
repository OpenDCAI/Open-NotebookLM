# PPT 产出信息、风格信息与大纲协同重构汇总

更新时间：2026-04-29

## 1. 背景问题

当前 PPT 产出链路已经从“直接进工作台生成 PPT”调整为“先生成产出文档和大纲，再通过专用 chat 调整”，但现有实现仍有几个明显问题：

1. `推送这版` 对用户来说没有明显效果。
   - 用户在 chat 里要求修改大纲后，界面上能看到候选回复，但正式产出文档和后续生成输入没有稳定同步。
   - 右侧 Markdown 产出文档、`output.outline`、`outline_chat_draft_outline` 三者之间的关系不够清晰。
   - 用户点击推送后，不容易判断“到底是候选被应用了，还是只是回复了一段文字”。

2. 产出文档结构不够贴近真实 PPT 工作流。
   - 现在主要是 `产出须知 + PPT 大纲`，缺少明确的风格层。
   - “商务风格 / 学术汇报 / 简洁干净”这类要求如果散落在大纲 chat 或所谓全局规则里，用户很难检查。

3. `全局规则` 是冗余抽象。
   - 用户不需要理解一个隐藏的 `outline_global_directives`。
   - 如果是整体表达风格，应该进入 `风格信息`。
   - 如果是具体页面要求，应该直接进入对应页的大纲字段。

4. 大纲修改需要更可靠的“先理解、再修改、再审核”链路。
   - 当前单次 LLM 直接改大纲，容易漏改、误改、或者回复说改了但结构没变。
   - 更合理的方式是类似 React 更新思路：先识别用户意图，生成变更计划，再产出新状态，最后 review 新状态是否符合用户意图。

## 2. 目标

PPT 产出文档应成为用户和 AI 共同维护的唯一可见状态。用户看到的右侧文档，就是后续进入 PPT 生成工作台的输入。

新的产出文档分为三块：

```markdown
# {PPT 产出标题}

## 产出信息

## 风格信息

## PPT 大纲
```

核心目标：

1. `产出信息` 记录本次产出的基础事实，不作为主要编辑区。
2. `风格信息` 记录整体表达风格、受众、语气、视觉倾向和补充提示词。
3. `PPT 大纲` 记录每一页的页面级内容，后续生成 PPT 时直接读取这里。
4. 所有信息都可以通过 PPT 专用 chat 修改，但修改必须进入候选态，用户点击应用后才覆盖正式状态。
5. 不再维护独立 `全局规则`，所有规则都落到 `风格信息` 或 `PPT 大纲` 内。

## 3. 新的产出文档结构

### 3.1 产出信息

`产出信息` 用来表达本次产出的基础元信息，通常由系统根据来源确认阶段自动生成。

建议字段：

```markdown
## 产出信息

- 产出类型：PPT
- 产出标题：SHRP 论文汇报
- 目标页数：10 页
- 面向对象：技术/产品/业务/学术评审
- 来源文件：Expert_attention____ACL_v2 (2).pdf
- 参考文档：梳理摘要1
- 生成状态：大纲讨论中
```

规则：

1. 这块默认不需要用户频繁改。
2. 用户明确要求时，chat 可以修改如 `产出标题`、`目标页数`、`面向对象`。
3. 来源文件、参考文档这类绑定关系不应由普通 chat 随意改，应通过来源确认或参考选择入口改。
4. 进入 PPT 工作台时，这块只作为生成上下文，不直接生成页面内容。

### 3.2 风格信息

`风格信息` 是替代 `全局规则` 的核心区域。

建议字段：

```markdown
## 风格信息

- 风格类型：商务风格
- 表达语气：简洁、清晰、结论先行
- 视觉倾向：浅色背景、少量强调色、图文平衡
- 受众假设：产品和业务团队，需要理解方法价值，不需要过多公式细节
- 补充提示词：
  - 用业务可理解的语言解释技术贡献
  - 每页标题尽量是结论句
  - 弱化训练细节，强化效果、部署价值和对比优势
```

预设风格可以先做轻量枚举：

1. `简洁干净`
   - 少文字、强结构、留白多。
   - 适合内部快速同步、短汇报。

2. `商务风格`
   - 结论先行、价值导向、适度包装。
   - 适合产品、业务、管理层沟通。

3. `学术汇报`
   - 背景、方法、实验、结论完整。
   - 适合论文组会、答辩、技术评审。

4. `自定义`
   - 用户通过 chat 或输入框补充。
   - 例如“像咨询公司路演”“更像课程讲义”“面向投资人”。

规则：

1. 所有整体表达要求都写进 `风格信息`，不再写入 `outline_global_directives`。
2. 如果用户说“整体更商务一点”，修改的是 `风格信息`，并可联动微调大纲标题和页面重点。
3. 如果用户说“第 3 页更商务一点”，则修改第 3 页大纲，不需要新增全局规则。
4. PPT 页面生成阶段必须读取 `风格信息`，并把它作为每一页生成 prompt 的稳定上下文。

### 3.3 PPT 大纲

`PPT 大纲` 是后续生成 PPT 的主体输入。

建议每页结构：

```markdown
## PPT 大纲

### 第 1 页：SHRP：面向高效编码器压缩的专业化头路由与剪枝

**页面定位**
标题页，建立主题和汇报范围。

**布局说明**
中央放置主标题和副标题，下方放作者/机构信息；背景简洁，突出 SHRP 关键词。

**页面要点**
- 结构化压缩框架：SHRP
- 核心目标：联合剪枝注意力头与前馈网络计算
- 最终产出：与标准推理引擎兼容的静态压缩编码器

**素材建议**
`/path/to/image.jpg`
```

规则：

1. 每一页是独立可选模块。
2. 用户点击右侧某一页卡片后，chat 默认围绕该页修改。
3. 用户不选页时，chat 按整体大纲修改。
4. 页级风格或页面特殊要求直接写进对应页，比如 `页面定位`、`布局说明` 或 `页面要点`。
5. 不再额外维护“全局规则”区域。

## 4. Chat 修改对象

PPT 专用 chat 可以修改三个区域：

1. 修改 `产出信息`
   - 例：“标题改成面向产品团队的 SHRP 价值汇报”
   - 影响：产出标题、面向对象、目标页数等。

2. 修改 `风格信息`
   - 例：“整体改成商务风格，少讲公式，多讲价值”
   - 影响：风格类型、表达语气、视觉倾向、补充提示词。

3. 修改 `PPT 大纲`
   - 例：“第 3 页突出专家注意力的直觉，不要太技术”
   - 影响：指定页的页面定位、标题、布局说明、页面要点、素材建议。

用户体验上，chat 不需要让用户选择“我要改哪个 JSON 字段”。系统通过意图识别自动判断。

## 5. 大纲修改的三段式 Agent 流程

建议把 `/outline-chat` 从“一次 LLM 直接改”升级为三段式：

```text
用户消息
  -> Planner：识别修改意图
  -> Editor：生成候选产出文档状态
  -> Reviewer：检查候选是否满足意图
  -> 返回候选改动 + 可读说明
```

### 5.1 Planner：识别意图

输入：

- 用户最新消息。
- 当前选中的页，若有。
- 当前正式产出文档三段内容。
- 当前候选产出文档三段内容，若有。
- 本 output 专用 chat history。

输出结构：

```json
{
  "scope": "output_info | style_info | outline | mixed",
  "target_slides": [3],
  "operation": "update | add | remove | reorder | rewrite | clarify",
  "user_intent": "把第 3 页改得更偏业务表达，弱化技术细节",
  "constraints": [
    "不要引入来源中没有的事实",
    "保持总页数不变"
  ],
  "needs_source_grounding": true
}
```

规则：

1. 如果用户选中了某页，但消息里没有明确整体修改，默认 `scope = outline` 且 `target_slides = [selected]`。
2. 如果用户说“整体”“全部页面”“风格”，默认影响 `style_info`，必要时联动 `outline`。
3. 如果用户说“标题、页数、面向对象”，默认影响 `output_info`。
4. 如果意图不清，返回澄清问题，不要强行改。

### 5.2 Editor：生成候选状态

输入：

- Planner 输出。
- 当前正式状态或当前候选状态。
- 来源 RAG 片段。
- 风格信息。

输出：

```json
{
  "draft_output_info": {},
  "draft_style_info": {},
  "draft_outline": [],
  "change_summary": "已将第 3 页改为业务价值表达，弱化训练细节",
  "assistant_message": "我先整理成一版候选修改，当前还没有覆盖正式大纲。"
}
```

规则：

1. Editor 必须返回完整候选状态，不只返回 diff 文本。
2. 未被修改的部分必须原样保留。
3. 修改页级内容时，不能破坏页面顺序和页码。
4. 如果修改会改变页数，必须明确说明。
5. 不允许把整体规则塞进隐藏字段；整体规则只能进 `风格信息`。

### 5.3 Reviewer：审核候选

输入：

- 用户原始消息。
- Planner 输出。
- 修改前状态。
- Editor 候选状态。

输出：

```json
{
  "passed": true,
  "issues": [],
  "fix_suggestions": [],
  "review_summary": "候选修改符合用户要求，未改变页数，未引入新事实。"
}
```

检查项：

1. 是否真的改到了用户要求的目标。
2. 是否误改了非目标页。
3. 是否违反来源事实。
4. 是否把风格规则写到了正确位置。
5. 是否仍保留完整 Markdown 可渲染结构。

如果 `passed = false`：

1. 可以让 Editor 自动修一轮。
2. 最多自动修一轮，仍失败则返回给用户说明问题。
3. 不要把不合格候选应用到正式产出文档。

## 6. 推送 / 应用候选的重新定义

建议把用户可见文案从 `推送这版` 改成更准确的：

- `应用候选修改`
- 或 `应用到产出文档`

原因：这里不是把内容“推送”到另一个地方，而是把候选状态覆盖为正式产出状态。

### 6.1 Chat 后的状态

用户发送 PPT 专用 chat 后：

1. 生成 `draft_output_info`、`draft_style_info`、`draft_outline`。
2. 右侧产出文档可以展示候选预览。
3. 正式状态不变。
4. 按钮显示 `应用候选修改` 和 `放弃候选`。

### 6.2 点击应用候选修改

点击后必须同时完成：

1. `output.output_info = draft_output_info`
2. `output.style_info = draft_style_info`
3. `output.outline = draft_outline`
4. 清空当前 active draft。
5. 重新生成右侧 Markdown 产出文档。
6. 更新当前 output 的 updated_at。
7. 新开一个 active chat session，后续继续基于正式状态聊。

用户能感知到的结果：

1. 右侧文档立即变成修改后的正式版本。
2. 页卡片内容立即变化。
3. `应用候选修改` 按钮消失。
4. AI 回复不再说“已经改完正式文档”，而是明确“候选已应用到产出文档”。

### 6.3 放弃候选

点击后：

1. 清空 draft。
2. 保持正式状态不变。
3. 右侧恢复正式产出文档。
4. chat 里记录一条轻量提示：已放弃本次候选修改。

## 7. 数据模型建议

现有模型里有：

```json
{
  "outline": [],
  "outline_global_directives": [],
  "outline_chat_draft_outline": [],
  "outline_chat_draft_global_directives": []
}
```

建议演进为：

```json
{
  "output_info": {
    "type": "ppt",
    "title": "",
    "page_count": 10,
    "audience": "",
    "source_names": [],
    "bound_document_titles": [],
    "stage_label": "大纲讨论中"
  },
  "style_info": {
    "preset": "business",
    "tone": "简洁、清晰、结论先行",
    "visual_style": "浅色背景、少量强调色、图文平衡",
    "supplement_prompt": []
  },
  "outline": [],
  "draft": {
    "output_info": {},
    "style_info": {},
    "outline": [],
    "change_summary": "",
    "review": {}
  }
}
```

兼容策略：

1. 第一阶段可以不立即迁移 manifest，只在服务层把旧字段映射成新结构。
2. `outline_global_directives` 暂时保留读取兼容，但不再写入新数据。
3. 历史数据如果有 `outline_global_directives`，打开时可以合并到 `style_info.supplement_prompt`。
4. 前端不再展示全局规则 UI。

## 8. Prompt 拼接逻辑

### 8.1 初始生成 PPT 大纲

输入应包含：

1. 来源 RAG 结果。
2. 用户选择的参考文档全文或选中模块。
3. 产出信息。
4. 风格信息初始值。
5. 用户补充目标。

输出必须包含：

1. `output_info`
2. `style_info`
3. `outline`

要求：

1. 最大标题用 `##`。
2. 页级标题用 `### 第 N 页：标题`。
3. 不生成隐藏全局规则。
4. 风格要求必须写进 `风格信息`。

### 8.2 大纲 chat

Prompt 结构：

```text
[系统角色]
你是 ThinkFlow 的 PPT 产出文档协同编辑助手。
你的任务是根据用户最新消息，生成候选修改，而不是直接覆盖正式产出文档。

[当前正式产出文档]
产出信息
风格信息
PPT 大纲

[当前候选产出文档]
如果存在 draft，则提供 draft；否则为空。

[当前选中页]
如果用户在右侧选中了某一页，提供页码和该页内容。

[来源 RAG 片段]
只使用用户最新消息作为 RAG query。
不要把完整组装 prompt 作为 embedding query。

[本 output 专用 chat history]
只包含用户对该 PPT 产出的 query 和 AI 回复。
不包含普通 chat 的组装上下文。

[用户最新消息]
```

输出结构：

```json
{
  "planner": {},
  "draft_output_info": {},
  "draft_style_info": {},
  "draft_outline": [],
  "review": {},
  "assistant_message": ""
}
```

## 9. 前端交互建议

右侧产出文档阅读态：

1. `产出信息` 是普通信息区。
2. `风格信息` 是可读卡片区，可以显示风格 preset、语气、视觉倾向、补充提示词。
3. `PPT 大纲` 按页卡片展示。
4. 点击页卡片选中当前页，chat 默认围绕该页。
5. 点击章节外层模块可以选择“本次应用候选修改的模块”，但页卡片点击不应触发外层模块选择。

中栏 PPT 专用 chat：

1. 标题：`PPT 产出文档讨论`。
2. placeholder 根据选择状态变化：
   - 未选页：`描述你想怎样调整产出信息、风格或整体大纲`
   - 已选页：`正在调整第 N 页，可以描述这页要怎么改`
3. 有候选修改时，显示：
   - `应用候选修改`
   - `放弃候选`
4. 不再出现 `全局规则` 文案。

左栏产出 tab：

1. 点击 PPT output 恢复该 output 的专用 chat 和右侧产出文档。
2. 不创建新的产出文档。
3. 不写入普通对话列表。

## 10. 后续实施切分

### Phase 1：文档结构收口

目标：

1. 右侧产出文档改为 `产出信息 / 风格信息 / PPT 大纲` 三段。
2. 生成初始大纲时输出三段内容。
3. 去掉新写入的 `outline_global_directives`。

涉及：

- `buildPptOutputDocumentContent`
- `OutputV2Service.create_outline`
- 初始 PPT outline prompt
- 右侧产出文档阅读态渲染

### Phase 2：应用候选修改真正生效

目标：

1. `/outline-chat` 返回三段 draft。
2. `应用候选修改` 同步更新正式 output 状态。
3. 右侧 Markdown 文档与 output 状态保持一致。
4. 清理“推送没有变化”的体验问题。

涉及：

- `OutputV2Service.outline_chat`
- `OutputV2Service.apply_outline_chat`
- `syncPptOutputDocument`
- `usePptOutlineManager`

### Phase 3：Planner / Editor / Reviewer

目标：

1. 引入三段式大纲修改链路。
2. Planner 识别改产出信息、风格信息、整体大纲还是单页。
3. Editor 生成完整候选状态。
4. Reviewer 检查是否符合用户意图。

涉及：

- `_build_outline_chat_intent_summary`
- `_apply_outline_chat`
- 新增 `_review_outline_chat_candidate`
- outline chat 测试用例

### Phase 4：去除全局规则 UI 和历史字段写入

目标：

1. 前端不再展示全局规则。
2. 后端不再写 `outline_global_directives` 和 `draft_global_directives`。
3. 历史数据兼容读取并迁移到 `style_info.supplement_prompt`。

涉及：

- `PptOutlinePanel`
- `usePptOutlineManager`
- `OutputV2Service._sync_outline_chat_state`
- 兼容测试

## 11. 验收标准

1. 点击生成 PPT 后，右侧出现三段式产出文档。
2. 用户说“改成商务风格”，`风格信息` 发生候选变化。
3. 用户选中第 3 页并说“这页少讲技术，多讲业务价值”，只有第 3 页候选大纲变化。
4. 点击 `应用候选修改` 后，右侧正式文档立即更新。
5. 再点击确认生成时，PPT 工作台读取的是应用后的正式三段内容。
6. 普通 chat history 不包含 PPT 专用 chat 的组装 prompt。
7. RAG query 只用用户最新消息，不用完整拼接 prompt。
8. 新数据不再产生 `outline_global_directives`。
9. 历史 output 打开不报错，旧全局规则能被合并进风格补充提示词。
10. 用户能够明确感知候选态、正式态、应用成功三个状态。

## 12. 一句话总结

PPT 产出不应该再是“一个大纲数组 + 隐藏全局规则”，而应该是用户可见的三段式产出文档：`产出信息` 定义任务，`风格信息` 定义表达方式，`PPT 大纲` 定义页面内容；chat 每次只生成候选状态，应用后才更新正式产出文档，并通过 Planner / Editor / Reviewer 保证修改真的生效。
