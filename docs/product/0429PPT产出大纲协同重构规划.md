# PPT 产出大纲协同重构规划

> 基于 `docs/product/0426产品交互逻辑梳理.md` 第 8 节，以及当前 `output_v2` / 前端 PPT outline-chat 代码结构整理。
> 本规划先只覆盖 PPT，报告、导图、播客等非 PPT 产出暂时不改。

## 1. 背景

0426 版本里，PPT 产出链路被描述为：

```text
选择来源与设定
-> 创建并生成初版产出文档
-> 立即进入产出工作台
-> 在产出工作台内确认大纲 / 生成 PPT / 逐页修改
```

但现在产品方向要调整为：

```text
点击 PPT 产出
-> 先确认来源范围
-> 先生成 PPT 大纲
-> 中栏继续用 chat 讨论和修改大纲
-> 用户显式确认 / 推送大纲
-> 再进入后续逐页生成与预览
```

核心变化不是“少一步”，而是把 PPT 生成前的确认过程从独立工作台前移到主工作区的对话流里。PPT 大纲不再是直接进入最终工作台后的静态预览，而是一个可以持续对话、产生候选改动、由用户确认的产出对象。

## 2. 当前代码现状

当前代码已经有一部分可复用能力：

文件：

- `fastapi_app/routers/kb_outputs_v2.py`
- `fastapi_app/services/output_v2_service.py`

已有接口：

```text
POST /api/v1/kb/outputs/{output_id}/outline-chat
POST /api/v1/kb/outputs/{output_id}/outline-chat/apply
POST /api/v1/kb/outputs/{output_id}/generate
```

已有 PPT 状态：

```text
outline_ready  -> 大纲阶段
pages_ready    -> 页面生成/确认阶段

```

已有 outline chat 数据结构：

```text
outline_chat_sessions
outline_chat_active_session_id
outline_chat_draft_outline
outline_chat_draft_global_directives
outline_chat_has_pending_changes
outline_chat_history
```

已有后端逻辑：

- `_sync_outline_chat_state()` 会为 PPT output 创建/同步 active outline chat session。
- `outline_chat()` 会基于当前大纲、来源快照、参考文档、指导、历史消息，生成候选大纲改动。
- `apply_outline_chat()` 会把候选 draft outline 合并为正式 outline。
- `save_outline(pipeline_stage="pages_ready")` 会把大纲推进到页面生成阶段。

### 2.2 前端已有能力

文件：

- `frontend/src/components/ThinkFlowWorkspace.tsx`
- `frontend/src/components/PptOutlinePanel.tsx`
- `frontend/src/components/PptPageReviewPanel.tsx`

已有前端逻辑：

- `confirmPptSourceLockIntent()` 调 `createOutline('ppt')`。
- `isPptOutlineChatStage` 判断当前是否处于 PPT 大纲 chat 阶段。
- `visibleChatMessages` 在 outline 阶段显示 PPT outline chat messages。
- `handlePptOutlineChatMessage()` 把中栏输入发送到 `/outline-chat`。
- `applyPptOutlineDraft()` 调 `/outline-chat/apply`，把候选大纲推送成正式大纲。
- `confirmPptOutline()` 调 `saveOutline({ pipelineStage: 'pages_ready' })`，进入下一阶段。
- `PptOutlinePanel` 右侧显示大纲、候选 diff、确认按钮。

### 2.3 当前主要问题

虽然代码已有大纲 chat 骨架，但产品语义和 UI 入口还没有完全对齐：

1. 0426 文档旧逻辑仍写着“创建成功后立即跳转到产出工作台”。
2. 前端文案仍有“来源锁定后直接进入 PPT 大纲阶段”，但没有把“这是一个可 chat 的大纲协同阶段”讲清楚。
3. 点击 PPT 后用户感知上仍容易理解成“马上进入产出工作台”，而不是“创建一个可讨论的大纲会话”。
4. `output_focus` / `output_immersive` 的工作区模式命名偏旧，容易和最终产出工作台混在一起。
5. 大纲 chat 现在和普通 chat 复用中栏，但需要更明确地区分：
   - 普通 chat 是知识问答和文档沉淀。
   - PPT outline chat 是只服务当前 PPT 大纲的结构协同。
   - PPT outline chat 不应该进入左侧「对话」tab，也不应该写入普通 `kb_chat_messages`。
6. “确认大纲”和“推送候选大纲”两个动作容易混淆：
   - 推送候选大纲：把 chat 产生的 draft 应用到 outline。
   - 确认大纲：锁定当前 outline，进入 pages_ready。

## 3. 目标流程

### 3.1 第一阶段：点击 PPT，不直接进入最终工作台

用户在右侧文档区或产出入口点击 `PPT` 后，不直接进入最终 PPT 预览/生成工作台。

应该先进入来源确认：

```text
点击 PPT
-> 弹出「确认本次 PPT 来源」弹窗
-> 展示本次会使用的来源文件、梳理文档、产出指导
-> 用户点击「确认并生成大纲」
```

来源确认的意义：

- 锁定本轮 PPT 的输入快照。
- 避免后续 chat 时来源集合动态变化，导致大纲上下文不稳定。
- 明确“这一次 PPT 大纲是基于哪些材料生成的”。

### 3.2 第二阶段：生成产出大纲

点击「确认并生成大纲」后：

```text
POST /api/v1/kb/outputs/outline
target_type = "ppt"
pipeline_stage = "outline_ready"
```

后端生成：

- `output` 记录。
- `outline` 页面级大纲。
- `outline_chat_sessions` 初始会话。
- `source_paths / source_names / bound_document_ids / guidance_snapshot_text` 来源快照。
- `result_path`，用于后续 Paper2PPT pipeline。

不做：

- 不直接调用 `/generate`。
- 不直接生成 PPTX。
- 不进入 `pages_ready`。
- 不把大纲直接视为用户已确认的最终结构。

### 3.3 第三阶段：进入 PPT 大纲协同视图

生成大纲后，界面进入一个“PPT 大纲协同视图”，而不是最终产出工作台。

推荐布局继续使用三栏思想：

```text
左栏：对话 / 素材 / 产出
中栏：PPT 大纲讨论 chat
右栏：PPT 大纲预览与候选改动面板
```

中栏标题：

```text
PPT 大纲讨论
```

中栏输入 placeholder：

```text
说说你想怎么调整这份 PPT，例如“压缩到 12 页，突出实验效果”
```

右栏显示：

- 当前 PPT 来源快照。
- 当前正式 outline。
- 如果有 draft，显示候选大纲 diff。
- 可操作按钮：
  - `推送这版`：应用 chat 产生的候选改动。
  - `确认大纲并进入生成`：只有没有 pending draft 时可点。

### 3.3.1 PPT 大纲 chat 的归属

PPT 大纲 chat 是一个**绑定产出物的专用 chat**，不是普通 notebook conversation。

归属关系：

```text
output_id
  └─ outline_chat_sessions[]
       ├─ session_id
       ├─ messages[]
       ├─ draft_outline
       ├─ draft_global_directives
       ├─ intent_summary
       └─ has_pending_changes
```

明确不做：

- 不在左侧「对话」tab 创建一条 conversation。
- 不写入 Supabase `kb_chat_messages`。
- 不复用普通 conversation 的 `conversation_id`。
- 不走 `/api/v1/kb/conversations/{id}/messages`。
- 不参与普通 notebook chat 的历史列表、标题、来源绑定、workspace-state。

前端只是临时把中栏从普通 chat renderer 切换为 `activeOutput.outline_chat_sessions` 的消息流。用户看到的是“同一个中栏”，但数据归属是 output，而不是左侧对话。

这样做的原因：

- PPT 大纲讨论是产出内部的编辑过程，不是知识问答对话。
- 它的历史只对这份 PPT 有意义。
- 它应该随 PPT output 一起恢复、归档、复制，而不是污染 notebook 的普通对话列表。
- 后续打开这个 PPT output，应恢复它自己的 outline chat，而不是跳回某条普通 conversation。

### 3.4 第四阶段：chat 修改大纲

用户在中栏发送消息：

```text
POST /api/v1/kb/outputs/{output_id}/outline-chat
```

请求输入：

```json
{
  "message": "把实验结果提前，并压缩背景页",
  "active_slide_index": 2,
  "conversation_history": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ]
}
```

注意：

- `conversation_history` 必须只来自当前 output 的 active outline chat session。
- 不应该把普通 chat 的完整 workspace prompt 混入。
- 不应该把左侧普通对话的历史直接混入。
- 如果确实要引用普通 notebook 对话，只能通过单独的「参考摘要」字段，且必须是显式摘要，不是原始 prompt/history。
- 当前代码使用 `buildConversationHistoryPayload(chatMessages)`，需要改为在 outline stage 下只传 `pptOutlineChatMessages` 或 active outline session messages，避免普通 chat 历史污染 PPT 大纲协同。

后端生成：

- `draft_outline`
- `draft_global_directives`
- `assistant_message`
- `intent_summary`
- `change_summary`

前端表现：

- 中栏出现用户消息和 AI 回复。
- 右栏出现候选 diff。
- 候选只是一版 draft，不立即覆盖正式大纲。

### 3.4.1 PPT chat 修改大纲的内部逻辑

PPT 大纲 chat 的一次请求不是普通问答，而是一次“候选结构编辑”。

推荐后端处理链路：

```text
用户消息
-> 读取当前 output
-> 读取当前正式 outline
-> 读取 active outline_chat_session
-> 读取当前 draft outline（如果已有 pending draft，以 draft 为编辑基底）
-> 识别用户意图
-> 定位修改范围
-> 生成 next_draft_outline
-> 生成 diff / change_summary / assistant_message
-> 保存到 active session
-> 返回 output + assistant_message
```

编辑基底规则：

```text
如果当前没有 pending draft：
  base_outline = output.outline

如果当前已有 pending draft：
  base_outline = active_session.draft_outline
```

这样用户可以连续说：

```text
用户：压缩到 12 页
AI：已生成候选大纲
用户：再把实验结果提前
AI：在上一版候选大纲基础上继续调整
```

而不是每轮都从正式 outline 重新生成，导致前一轮未推送的候选被覆盖。

### 3.4.2 意图识别

每条用户消息先归类为大纲编辑意图。

建议识别维度：

```text
scope:
  - global：整套 PPT 规则，例如“所有标题短一点”“整体更学术”
  - outline：整体结构，例如“压缩到 12 页”“把实验提前”
  - slide：单页修改，例如“第 3 页加 ablation”
  - source_question：询问来源或当前大纲，不产生结构改动

operation:
  - add_slide
  - remove_slide
  - merge_slides
  - split_slide
  - reorder
  - rewrite_title
  - rewrite_points
  - change_tone
  - change_layout
  - change_page_count
  - no_change

targets:
  - page numbers
  - current focused slide
  - title keywords
  - section range
```

输出结构建议：

```json
{
  "mode": "outline",
  "operations": [
    {
      "type": "change_page_count",
      "target": "deck",
      "value": 12,
      "instruction": "压缩到 12 页"
    },
    {
      "type": "reorder",
      "target": "section:实验结果",
      "position": "earlier",
      "instruction": "实验结果提前"
    }
  ],
  "requires_outline_change": true
}
```

当前代码里已经有 `_build_outline_chat_intent_summary()`，但它偏轻量规则识别。第一版可以继续沿用，后续再把 intent summary 独立成更结构化的 LLM/规则混合分类。

### 3.4.3 修改范围定位

定位优先级：

```text
1. 用户显式页码：第 3 页、第 5-7 页
2. 当前 UI 焦点页：active_slide_index
3. 用户提到的标题关键词：实验、方法、结论
4. 全局词：整体、全部、每页、整套
5. 默认：outline 级修改
```

例子：

```text
“第 4 页加一张对比表”
-> scope = slide
-> target = page 4

“把实验结果提前”
-> scope = outline
-> target = section/title contains 实验结果

“所有标题短一点”
-> scope = global
-> target = outline_global_directives
```

### 3.4.4 候选 draft 生成

模型不直接覆盖正式大纲，只产出候选 draft。

输入：

```text
系统角色：PPT 大纲协同编辑助手
来源快照：source_summary / source_names
产出指导：guidance_snapshot_text
正式 outline：output.outline
当前候选 outline：active_session.draft_outline（如有）
当前全局规则：outline_global_directives
当前候选规则：draft_global_directives
active_slide_index
当前 output 专用 chat 历史
用户最新消息
```

输出：

```json
{
  "draft_outline": [],
  "draft_global_directives": [],
  "assistant_message": "已将实验结果提前，并把整体页数压缩为 12 页。",
  "change_summary": "调整页序、压缩页数",
  "intent_summary": {}
}
```

约束：

- 必须返回完整可用 outline，而不是 patch 片段。
- 页码 `pageNum` 重新连续编号。
- 每页保留 `title / layout_description / key_points`。
- 不允许引用来源中不存在的事实。
- 如果用户只是提问，例如“现在一共多少页？”，则返回 `requires_outline_change=false`，不生成 draft。

### 3.4.5 Diff 与确认

前端收到 `draft_outline` 后：

```text
正式 outline vs draft_outline
-> diffPptOutline()
-> 右栏展示新增 / 删除 / 修改
```

中栏 assistant message 只说明候选变化，不声称已经修改正式大纲。

推荐文案：

```text
我生成了一版候选大纲：压缩到 12 页，并把实验结果提前到方法之后。右侧可以预览变化，确认后点击“推送这版”。
```

禁止文案：

```text
我已经修改了大纲。
```

因为在用户点击推送之前，正式 outline 还没有变化。

### 3.5 第五阶段：推送候选大纲

用户点击对话中的 `推送这版` 或右栏对应按钮：

```text
POST /api/v1/kb/outputs/{output_id}/outline-chat/apply
```

效果：

- 把 `outline_chat_draft_outline` 应用到正式 `outline`。
- 把本次 active session 标记为 applied 或归档。
- 新建下一轮 active outline chat session。
- 清空 pending draft 状态。

这一步仍然不生成 PPT。

### 3.5.1 放弃候选大纲

需要规划一个“放弃候选改动”的入口，否则用户生成 draft 后只能推送或卡住。

推荐：

```text
右栏候选 diff 面板：
[推送这版] [放弃候选]
```

放弃效果：

- 清空 active session 的 `draft_outline`，恢复为正式 `outline`。
- 清空 `draft_global_directives` 或恢复为正式 `outline_global_directives`。
- `outline_chat_has_pending_changes = false`。
- 在 output 专用 chat 里追加一条 system message：

```text
已放弃上一版候选大纲，继续基于当前正式大纲讨论。
```

第一版如果不做放弃按钮，也必须在文档里明确 pending draft 的处理方式。否则“确认大纲”会因为 pending 状态被禁用，用户容易不知道怎么继续。

### 3.6 第六阶段：确认大纲并进入生成

当用户认为当前正式 outline 可以进入 PPT 页面生成时，点击：

```text
确认大纲并进入生成
```

调用：

```text
PUT /api/v1/kb/outputs/{output_id}/outline
pipeline_stage = "pages_ready"
```

前置约束：

- 如果存在 `outline_chat_has_pending_changes = true`，禁止确认。
- 提示用户先 `推送这版` 或放弃候选改动。

进入 `pages_ready` 后：

- 大纲锁定。
- 显示页面生成/确认面板。
- 用户可点击 `生成 PPT`，再调用 `/generate`。

## 4. 状态机

```text
idle
  |
  | 点击 PPT
  v
source_confirming
  |
  | 确认并生成大纲
  v
outline_generating
  |
  | create_outline 成功
  v
outline_ready
  |
  | 用户 chat 修改
  v
outline_draft_pending
  |
  | 推送这版
  v
outline_ready
  |
  | 确认大纲并进入生成
  v
pages_ready
  |
  | 生成 PPT
  v
generating
  |
  | 生成完成
  v
generated
```

关键约束：

- `outline_ready` 和 `outline_draft_pending` 都属于“大纲协同阶段”。
- `pages_ready` 才是后续 PPT 页面生成阶段。
- `generated` 才是最终产出预览/下载阶段。
- `outline_draft_pending` 下不能直接进入 `pages_ready`。

## 5. 前端改造点

### 5.1 入口文案与行为

当前：

```text
确认后将直接进入 PPT 大纲阶段
```

建议调整为：

```text
确认后会先生成一版 PPT 大纲，并在中间对话区继续讨论和调整；确认大纲后才进入逐页生成。
```

按钮：

```text
确认并生成大纲
```

不使用：

```text
创建并生成初版
进入工作台
生成 PPT
```

### 5.2 命名收口

建议在前端语义上区分三个概念：

```text
PPT 大纲协同视图：outline_ready 阶段，中栏可 chat。
PPT 页面生成视图：pages_ready 阶段，右栏逐页确认/生成。
PPT 产出结果视图：generated 阶段，预览和下载。
```

现有 `output_focus` 可以暂时保留，但 UI 文案不要叫“产出工作台”，避免和最终生成阶段混淆。

### 5.3 中栏 chat 切换

当前 `ThinkFlowWorkspace` 已有：

```text
isPptOutlineChatStage
visibleChatMessages
handlePptOutlineChatMessage()
```

需要检查并确保：

- 进入 `outline_ready` 后，中栏显示的是当前 output 的 outline chat messages。
- 用户发送消息走 `handlePptOutlineChatMessage()`。
- 普通 notebook chat history 不污染 outline chat history。
- 发送 outline chat 时，不调用 `appendConversationMessages()`。
- 不创建 / 更新普通 `conversationId`。
- 不刷新左侧 conversation list。
- 不调用 `/api/v1/kb/conversations/{conversation_id}/messages`。
- output 专用 chat 的消息只从 `activeOutput.outline_chat_sessions` 来。
- 离开当前 PPT output 后，普通 chat 恢复原状态。

中栏组件可以继续复用 `ThinkFlowCenterPanel` 的消息渲染能力，但数据源必须分叉：

```text
普通模式：
  messages = chatMessages
  onSend = handleNotebookChatMessage
  persistence = kb_chat_messages

PPT 大纲模式：
  messages = buildOutlineChatMessages(activeOutput)
  onSend = handlePptOutlineChatMessage
  persistence = output.outline_chat_sessions
```

### 5.3.1 左侧对话列表隔离

PPT 大纲 chat 不应该出现在左侧「对话」tab。

左侧「对话」tab 只展示普通 notebook conversations：

```text
conversationList = GET /api/v1/kb/conversations
```

PPT 大纲 chat 的入口应该在左侧「产出」tab：

```text
产出 tab
  - PPT：SHRP 汇报
    状态：大纲讨论中
    点击后恢复该 output 的 outline chat
```

如果用户在 PPT 大纲模式中点击左侧普通对话：

```text
退出当前 output 视图
恢复普通 chat
加载所选 conversation messages
右栏恢复普通文档区
```

如果用户在普通 chat 中点击左侧 PPT output：

```text
进入该 output 的当前 stage
如果 stage = outline_ready：中栏切为 output 专用 outline chat
如果 stage = pages_ready/generated：中栏可以隐藏或显示阶段说明，右栏展示页面生成/结果
```

### 5.4 右栏大纲面板

`PptOutlinePanel` 应作为大纲协同阶段的主右栏。

需要明确显示：

- 当前正式大纲。
- 当前焦点页。
- 来源锁定摘要。
- 候选 diff。
- `推送这版` 状态。
- `确认大纲并进入生成` 状态。

按钮禁用规则：

```text
有 pending draft：
  - 禁用「确认大纲并进入生成」
  - 展示提示：先推送或放弃候选改动

正在保存 / 生成：
  - 禁用所有结构性操作
```

### 5.5 左栏产出 tab

创建 PPT 大纲后，左栏产出 tab 应出现该 output：

```text
PPT · outline_ready
标题
来源数 / 页数 / 更新时间
```

点击该条目：

- 恢复到 PPT 大纲协同视图。
- 如果已经 `pages_ready` 或 `generated`，恢复对应阶段。

## 6. 后端改造点

### 6.1 create_outline 保持只生成大纲

当前 `OutputV2Service.create_outline(target_type="ppt")` 已经基本符合：

```text
target_type = ppt
stage = outline_ready
不调用 generate_output
```

需要确认：

- 接口返回中包含完整 `outline_chat_sessions`。
- 初始 assistant message 表达的是“大纲已生成，可以继续讨论修改”，不是“已经完成 PPT”。
- `source_summary` 足够支持后续 outline chat。

### 6.2 outline_chat 的 history 边界

需要确保 `outline_chat()` 接收到的 history 不包含普通 chat 的完整上下文 prompt。

建议约束：

```text
outline_chat.conversation_history 只允许当前 output 的 active outline chat session messages。
```

如果要引用普通 chat，应新增独立字段，例如：

```json
{
  "notebook_context_summary": "用户之前在普通对话中确认：这份 PPT 面向产品团队，重点讲 SHRP 的贡献。"
}
```

不能直接把普通 chat messages 混入 `conversation_history`。

后端保存位置：

```text
output manifest
  -> outline_chat_sessions[]
     -> messages[]
```

不保存到：

```text
Supabase kb_chat_messages
conversation_workspace_state
普通 conversation history sidecar
```

### 6.3 apply_outline_chat 不进入生成

`apply_outline_chat()` 只更新正式 outline，不改变 pipeline stage。

必须保持：

```text
pipeline_stage = outline_ready
```

### 6.4 save_outline 进入 pages_ready

`save_outline(pipeline_stage="pages_ready")` 是唯一从大纲协同进入页面生成准备阶段的入口。

必须保持当前保护：

```text
如果 outline_chat_has_pending_changes = true，禁止进入 pages_ready。
```

### 6.5 generate_output 只在 pages_ready 后可用

`generate_output()` 应只允许在 `pages_ready` 阶段被用户触发。

如果当前仍支持从 `outline_ready` 直接 generate，需要加保护。

## 7. 提示词与上下文规则

### 7.1 生成初始 PPT 大纲

输入优先级：

```text
1. 原始来源内容
2. 用户选择的梳理文档主文 / 模块
3. 产出指导
4. 用户的一句话目标 / 页数 / 风格 / 受众
```

输出要求：

```text
页面级大纲，不是文档章节。
每页包含：
- pageNum
- title
- layout_description
- key_points
- asset_ref 可选
```

### 7.2 大纲 chat

大纲 chat 的系统角色：

```text
你是 ThinkFlow 的 PPT 大纲协同编辑助手。
你的任务是根据用户最新要求产出候选大纲改动。
候选改动不会自动覆盖正式大纲，只有用户点击推送才生效。
```

必须强调：

- 不要无故重写整套结构。
- 用户要求全局调整时可以改全局规则。
- 用户要求当前页调整时优先改当前页。
- 事实必须服从来源，不编造来源里没有的结论。
- 你的输出是候选改动，不是最终修改。
- 只有用户点击“推送这版”后，候选改动才会覆盖正式大纲。

推荐 prompt 结构：

```text
[角色]
你是 ThinkFlow 的 PPT 大纲协同编辑助手。

[当前任务]
根据用户最新消息，生成一版候选 PPT 大纲改动。
不要直接声称已经修改正式大纲。

[来源快照]
source_summary

[产出指导]
guidance_snapshot_text

[正式大纲]
output.outline

[当前候选大纲]
active_session.draft_outline 或空

[当前全局规则]
outline_global_directives

[候选全局规则]
draft_global_directives

[当前焦点页]
active_slide_index

[本产出专用 chat 历史]
active_session.messages 最近 N 条

[用户最新消息]
message

[输出要求]
返回完整 draft_outline、draft_global_directives、intent_summary、assistant_message。
```

普通 notebook chat 的上下文不属于这个 prompt。

### 7.3 生成 PPT 页面

只在用户确认大纲后执行。

输入：

```text
确认后的正式 outline
来源快照
产出指导
页面生成规则
```

不要使用：

```text
未推送的 draft outline
普通 chat 的系统 prompt
未锁定的新来源
```

## 9. 实施拆分

### Phase 1：产品文案与入口收口

目标：

- 点击 PPT 后只表达“确认来源并生成大纲”。
- 去掉“直接进入产出工作台”的感知。
- 进入 outline_ready 后，中栏标题、placeholder、右栏说明都指向“大纲协同”。

涉及：

- `usePptOutlineManager.openPptSourceLockIntent`
- `ThinkFlowWorkspace` 的来源确认弹窗文案
- `PptOutlinePanel` 标题、按钮、提示

### Phase 2：大纲 chat history 边界检查

目标：

- outline chat 不吃普通 chat 的组装上下文。
- history 只保留用户对 PPT 大纲的 query 和 AI 的回复。
- outline chat 不写入普通 conversation，也不出现在左侧「对话」tab。
- 切换 output 时恢复 output 自己的 outline chat。

涉及：

- `handlePptOutlineChatMessage`
- `buildOutlineChatMessages`
- `/outline-chat` request payload
- `OutputV2Service._build_outline_chat_feedback`
- `OutputV2Service.outline_chat`
- `OutputV2Service._sync_outline_chat_state`

### Phase 2.1：大纲修改策略细化

目标：

- 连续 chat 时基于当前 draft 继续修改。
- 支持全局规则、整体结构、单页修改三种 scope。
- AI 回复明确“这是候选改动”。
- 右栏 diff 成为用户确认的主要依据。

涉及：

- `_build_outline_chat_intent_summary`
- `_apply_outline_chat`
- `_summarize_outline_chat_change`
- `diffPptOutline`
- `PptOutlinePanel` 的候选 diff 面板

### Phase 2.2：放弃候选改动

目标：

- pending draft 不再把用户卡死。
- 用户可以明确放弃候选，回到正式 outline 继续聊。

建议新增：

```text
POST /api/v1/kb/outputs/{output_id}/outline-chat/discard
```

或复用现有 apply 接口加 `action=discard`，但独立接口更清晰。

后端效果：

- active session draft 恢复为正式 outline。
- pending false。
- 追加 system message。

### Phase 3：状态机保护

目标：

- pending draft 时不能确认大纲。
- outline_ready 不能直接 generate。
- apply draft 不推进 stage。

涉及：

- `PptOutlinePanel` 按钮状态
- `OutputV2Service.save_outline`
- `OutputV2Service.generate_output`
- 后端测试

### Phase 4：左栏产出恢复与阶段展示

目标：

- 左栏产出 tab 能区分大纲阶段、页面阶段、已生成。
- 点击产出项恢复正确阶段。

涉及：

- `ThinkFlowLeftSidebar`
- `openExistingOutput`
- `normalizePptStage`

### Phase 5：验收与回归

目标：

- 覆盖完整 PPT 大纲协同链路。
- 确认非 PPT 产出不受影响。

## 10. 验收标准

### 10.1 新建 PPT 产出

- 点击 PPT 后出现来源确认弹窗。
- 弹窗文案明确“先生成大纲，可继续对话调整”。
- 点击确认后，生成 `outline_ready` 的 PPT output。
- 不自动调用 `/generate`。
- 不出现 PPTX 下载结果。

### 10.2 大纲协同

- 中栏进入 `PPT 大纲讨论`。
- 初始 AI 消息说明当前大纲结构。
- 用户发送“压缩到 12 页”等请求后，产生候选改动。
- 右栏显示候选 diff。
- 候选改动未推送前，正式 outline 不被覆盖。

### 10.3 推送候选大纲

- 点击 `推送这版` 后，draft 应用为正式 outline。
- pending 状态清空。
- 生成新的 active outline chat session。
- 仍处于 `outline_ready`。

### 10.4 确认大纲

- 没有 pending draft 时，可以点击 `确认大纲并进入生成`。
- 有 pending draft 时，按钮禁用或后端返回明确错误。
- 确认后进入 `pages_ready`。
- 大纲锁定，不能继续用 outline chat 修改正式大纲。

### 10.5 生成 PPT

- 只有 `pages_ready` 阶段可以生成 PPT。
- 生成完成后进入 `generated`。
- 左栏产出 tab 显示该产出物。

### 10.6 history 不污染

- PPT outline chat history 只保存大纲讨论问答。
- 不保存组装后的 prompt。
- 不混入普通 chat 的 RAG context。
- 普通 chat 与 PPT outline chat 切换后，各自历史保持独立。
- PPT outline chat 不出现在左侧普通对话列表。
- PPT outline chat 不写 Supabase `kb_chat_messages`。
- 打开同一个 PPT output 时，恢复的是该 output 自己的 outline chat session。

### 10.7 大纲修改逻辑

- 连续多轮大纲 chat 会基于当前 draft 继续修改。
- 单页修改只影响目标页，除非用户明确要求整体重排。
- 全局规则修改会进入 `draft_global_directives`。
- 用户只是问问题时，不产生 pending draft。
- AI 回复必须表达“候选改动”，不能声称正式大纲已经被修改。
- 点击「推送这版」后，正式 outline 才变化。
- 点击「放弃候选」后，pending 状态清空，正式 outline 不变化。

## 11. 与 0426 文档的差异

旧版：

```text
创建产出文档成功后，页面立即跳转到产出工作台。
产出工作台中没有中栏对话区。
用户主要直接编辑左侧文档，偶尔用一次性 AI 优化大纲。
```

新版：

```text
点击 PPT 后，先生成一个可对话的 PPT 大纲产出。
主工作区保留中栏 chat，用于持续讨论大纲。
AI 的大纲修改先进入候选态，用户推送后才覆盖正式大纲。
确认正式大纲后，才进入后续页面生成 / PPT 预览阶段。
```

可以理解为：

```text
0426 的「产出工作台阶段 A：确认大纲」
被前移并升级为「PPT 大纲协同阶段」
```

## 12. 推荐实现结论

推荐沿用当前 `output_v2` 的 PPT outline-chat 骨架，不重建新系统。

第一轮代码改动应优先做：

1. 收口 PPT 入口和文案，让用户明确“先生成大纲，不直接生成 PPT”。
2. 强化 `outline_ready` 阶段的中栏 chat 和右栏大纲协同 UI。
3. 检查并修正 outline chat history 边界，避免普通 chat prompt 污染。
4. 加状态机保护：pending draft 不能确认，outline_ready 不能直接 generate。

这样改动最小，且和当前已有代码结构最匹配。
